# 游戏研发自动化 Agent —— A2A 架构与角色契约

> **阅读约定**：技术标识符首次出现时附中文注释，写法如 `Agent Card`（智能体能力名片）、`artifact`（产物文件），后续不再重复。
> **口径约定**：本文描述的是**已在本机跑通的实现**，每个角色都能通过 `http://localhost:900x/.well-known/agent-card.json` 被发现、被调用。未实现的能力会明确标注"预留"。

---

## 一、为什么用 A2A 而不是普通 HTTP 接口

一个自然的疑问：既然都是内部调用，为什么不用简单的 REST 接口，非要套一层 A2A（Agent-to-Agent，智能体间通信协议）？

| 维度 | 普通 REST | A2A |
|---|---|---|
| 服务发现 | 地址写死在配置里，加角色要改配置 | 通过 `/.well-known/agent-card.json` 自描述，编排器只需知道根地址 |
| 能力描述 | 靠文档或口头约定 | Agent Card 里声明 skill 名称、描述、输入输出模式，编排器可枚举 |
| 任务生命周期 | 需要自己定义状态字段 | 协议内置 `submitted / working / completed / failed / canceled` 状态机 |
| 长任务与流式 | 自己实现 SSE/轮询 | 协议内置 `TaskStatusUpdateEvent`（任务状态更新事件）与 `TaskArtifactUpdateEvent`（产物更新事件） |
| 跨厂商互通 | 私有协议 | 开放标准，未来接第三方 Agent（如外部 3D 生成服务）不需要改协议层 |

对本项目而言，A2A 最直接的收益是 **"加角色 = 加一个服务"**：新角色只要实现 `handle()` 并注册 Agent Card，编排器无需改动即可发现它。这一点在后续从 10 并发扩到 1000 并发、或把 3D 生成换成外部服务时尤为关键。

`a2a-sdk` 0.3.0 的实际集成方式（`app/agents/base.py`）：

```
SkillAgent（业务逻辑，实现 handle(payload) -> dict）
    ↓ 由 A2AExecutorWrapper 适配
AgentExecutor（协议层：发 working → 执行 → 发 DataPart artifact → 发 completed/failed）
    ↓ 由 build_uvicorn_server 包装
A2AStarletteApplication + uvicorn（每个 Agent 一个独立端口）
```

业务代码不感知协议：`handle()` 收到的是普通 dict，返回的也是普通 dict，协议适配只在 `A2AExecutorWrapper` 一处完成。

## 二、9 个服务的端口与职责

| 端口 | 服务 | 输入 | 输出（artifact） | 失败时谁负责 |
|---|---|---|---|---|
| 9000 | `orchestrator` | 自然语言文本 | 任务状态、检查点流水、最终汇总 | — |
| 9001 | `spec_agent` | 需求文本 + RAG 上下文 | 规格 JSON（含 3~20 条可执行断言、机制依赖） | 规格不合格由编排器判失败，不进入编码 |
| 9002 | `engineer_agent` | 规格 + 资产清单 +（可选）失败断言 | `versions/game_vN.html` 及契约声明 | 唯一可改代码的角色，修复责任可追溯 |
| 9003 | `modeler_agent` | 资产清单 | `assets/*.png`、`*.glb`、`manifest.json` | 资产缺失由 `reviewer` 的 error 级问题回退重建 |
| 9004 | `qa_agent` | 构建入口 + 断言列表 | 逐条断言结果、截图、运行错误 | 失败断言回退给 9002 |
| 9005 | `reviewer_agent` | 构建产物 | 静态审查报告（error / warn） | error 级阻塞交付 |
| 9006 | `player_sim_agent` | 部署 URL + 并发参数 | 玩家行为事件流 | 不作为交付门禁，属分析阶段 |
| 9007 | `market_agent` | 行为事件 | 留存/付费/流失报告 | 同上 |
| 9008 | `build_agent` | 任务目录 | H5 包、部署 URL、APK 状态 | 失败只影响交付，不影响"游戏可玩"判定 |

**关键设计**：9001~9005 是**质量门禁链**（不合格就不交付），9006~9007 是**分析链**（不影响交付，只提供决策参考），9008 是**交付链**。三条链的失败语义完全不同，混在一起会导致"APK 没打出来就认为游戏不可玩"这类误判。

## 三、编排主链路（可直接讲的一条线）

```
用户文本
  ↓ BERT 意图识别（本地 bert-base-chinese，规则兜底）
  ├─ new_requirement ─────────────────────────────────────────────┐
  ├─ query  → 返回任务状态与断言汇总                               │
  └─ fix    → 回到产物所有者（engineer_agent）+ 上一版代码          │
                                                                  ↓
  ① spec_agent      需求 → 规格契约（RAG 检索设计模式/引擎文档，重排序后注入）
                                                                  ↓
  ② engineer_agent ∥ modeler_agent（并行）
       编码生成 game.html        ∥    文生图/占位降级 → assets/
                                                                  ↓
  ③ qa_agent ∥ reviewer_agent（并行）
       真实 Chromium 跑断言      ∥    静态审查（契约完整性/资产存在性/XSS）
                                                                  ↓
  ④ 失败？ → 图数据库查询受影响机制 → 只把失败断言路由回 engineer_agent
       修复轮次上限 MAX_FIX_ROUNDS，到顶仍失败 → 判 failed（不伪装成功）
                                                                  ↓
  ⑤ build_agent      H5 打包 + 部署 + （可选）APK 构建
                                                                  ↓
  ⑥ player_sim_agent → 并发玩家实验（合成行为，标注非真人）
                                                                  ↓
  ⑦ market_agent     → 留存/付费/流失报告 + 改进建议
                                                                  ↓
  任务状态：completed / failed（状态以数据库为权威源，Redis 只做缓存）
```

**两个并行点**（面试可强调）：`②` 编码与素材互不依赖，并行省下素材生成时间；`③` 运行时验证与静态审查关注不同失效模式，并行且互为补充。

## 四、状态机与一致性约束

多 Agent 流水线最容易出的不是"能力不够"，而是**状态不一致**：编排器认为成功、数据库认为失败、用户看到的是第三种。本项目的三条硬约束：

### 4.1 单一权威源

| 数据 | 权威源 | 缓存/派生 |
|---|---|---|
| 任务状态 | MySQL `tasks.status`（不可用时降级 SQLite） | Redis `task:{id}:status`（可丢，读不到回落 DB） |
| 检查点流水 | MySQL `task_checkpoints` | — |
| 产物 | 文件系统 `generated/{task_id}/` + 哈希 | 数据库存路径与 sha256 |
| 机制依赖图 | Neo4j（不可用时降级 JSON 文件） | — |

Redis 只做加速，**任何写 Redis 失败都不影响任务结果**——这一点在早期版本里是 bug 源（Redis 不可用时状态写不进去，但 DB 写成功了，两边不一致）。

### 4.2 任务状态迁移

```
submitted → working → completed
                    ↘ failed
```

不允许从 `completed` 回到 `working`。修复请求（`fix` 意图）对已 `completed` 的任务会**新建一轮**并回到 `working`，轮次号递增，历史产物保留在 `versions/` 目录，不会覆盖。

### 4.3 产物版本化

`engineer_agent` 每次生成都写入新的版本文件 `versions/game_v1.html`、`game_v2.html`…，而不是覆盖 `game.html`。三个好处：

1. 修复时可以携带上一版代码，避免"重写把已通过的断言弄坏"；
2. QA 失败时能对比两版差异，定位是哪次修改引入的回归；
3. 面试演示时可以直接展示"v1 有 bug、v2 修好"的证据链。

## 五、角色协作契约（最容易被追问的部分）

### 5.1 规格契约：把"口语需求"变成"可判定标准"

`spec_agent` 的输出必须通过 `GameSpecContract`（游戏规格契约）校验（`app/contracts.py`）：

```python
class GameSpecContract(BaseModel):
    name: str                          # 游戏名称
    core_loop: str                     # 核心玩法循环
    entities: list[str]                # 实体清单
    rules: list[str]                   # 规则
    win_condition: str                 # 胜利条件
    lose_condition: str                # 失败条件
    acceptance_assertions: list[AssertionContract]   # 3~20 条
    mechanisms: list[dict]             # 机制依赖
```

其中断言类型被**限定在 6 种可执行检查**内：

| check_type | 含义 | QA 如何验证 |
|---|---|---|
| `start` | 页面加载后进入 playing 状态 | 读 `window.__game.state()` + 检查 canvas 尺寸 |
| `controls` | 方向键能移动玩家 | 发真实 `ArrowLeft/ArrowRight` 键事件，比对玩家坐标变化 |
| `score` | 核心动作后分数变化 | 调 `window.__game.action(...)`，比对 score 增量 |
| `win` | 达到目标分数进入 win | 驱动玩法直到 target，检查状态 |
| `win_text` | 胜利文案真实可见 | 状态为 win **且** DOM 可见 **且** 文本与规格一致 |
| `lose` | 漏接到上限进入 lose | 驱动玩法直到 miss 上限，检查状态 |

**为什么限定 6 种**：模型很容易写出"游戏应该好玩"这种断言，但它不可执行。限定类型后，写不出可执行断言的规格**直接判失败**，而不是"先跑起来再说"——这是整条流水线可信度的地基。

### 5.2 失败路由：按产物所有权回退

QA 报失败后，编排器不是无脑重跑全流程，而是：

1. 用 Neo4j 查机制依赖图，找出**受影响的机制范围**（`impacted_by(mech_id, max_depth=2)`）；
2. 按所有权表确定该回退给谁——代码问题回 `engineer_agent`，资产问题回 `modeler_agent`，规格问题回 `spec_agent`；
3. 携带这一轮的失败断言 + 受影响机制 + 上一版代码，让生产者**只改相关部分**。

### 5.3 验证者与生产者分离

`qa_agent` 和 `reviewer_agent` 都不能修改代码。这条约束看起来只是"分工"，实际是质量门禁能否成立的前提：如果编码者能自己判定合格，那"通过"就失去了信息量。

## 六、实测中踩到的三个真问题（面试可当"我踩过坑"讲）

### 6.1 A2A 根路由 404：服务健康但调不通

**现象**：9 个服务全部 `/.well-known/agent-card.json` 返回 200，但编排器向下游 `POST /` 发 `message/send` 时返回 404。

**定位过程**：先用 Starlette `TestClient` 直连应用，请求正常；用 uvicorn 单独起服务也正常。差异只在"多服务同进程并行启动"时出现。最后用 ASGI 包装器打印真实 `scope`，发现请求路径变成了 `http://localhost:9002/`（absolute-form，绝对 URI 形式），而不是 `/`。

**根因**：系统里设置了 `HTTP_PROXY`（本地代理软件常见），`httpx` 默认 `trust_env=True`，把发往 `127.0.0.1` 的请求交给了代理，代理以 absolute-form 转发，服务端路由匹配 `/` 失败。

**修复**：所有内部 A2A 调用统一 `trust_env=False`（`app/a2a.py`、`app/orchestrator.py`、`app/frontend.py`）。

**为什么值得讲**：这是"健康检查通过 ≠ 接口可用"的典型例子。只做健康检查会漏掉真实调用链的错误。

### 6.2 BERT 意图识别静默降级

**现象**：日志里意图识别一直显示 `method: rule`，从未走过 BERT。

**定位过程**：直接实例化 `BERTIntentClassifier` 并打印异常，发现 tokenizer 加载失败——模型目录是 `bert-base-chinese/bert-base-chinese/`（多套了一层），而配置指向 `bert-base-chinese/`。

**修复**：`config.py` 里增加候选路径探测（先试直接路径，再试嵌套路径），并且**降级时写日志与健康检查字段**，不再静默。降级仍有规则兜底，但用户能看到"当前是规则模式"。

**教训**：降级必须可见。静默降级会让"用了本地小模型"这种卖点在演示时当场穿帮。

### 6.3 QA 假通过：状态写了 win，文案没显示

**现象**：游戏实际玩到目标分数后画面没有出现"恭喜通关"，但 QA 判定通过。

**定位过程**：早期 QA 只检查 `window.__game.state() === 'win'`。但模板里胜利文案的 DOM 元素被 CSS 隐藏（`display:none` 未切换），状态是 win 而用户什么都看不到。

**修复**：`win_text` 断言改为三重判定——状态为 win **且** DOM 元素可见（`offsetParent !== null` 或计算样式非 none）**且** 文本与规格一致。同时补了反例测试 `tests/test_qa_runtime.py::test_win_text_hidden_must_fail`，防止回归。

**为什么值得讲**：这说明"自动测试"最容易骗自己——测试和目标不一致时，通过率是负数。

## 七、扩展到 100/1000 并发 AI 玩家的架构预留

面试官明确提到"先测 100 个玩家，再上 1000 个"。当前 Demo 实测 8~10 并发（`SIM_CONCURRENCY`，默认 10；会话数由 `SIM_SESSIONS_PER_PLAYER` 控制），上限受两处限制，且都已预留扩展点：

| 瓶颈 | 现状 | 扩展方式 |
|---|---|---|
| 浏览器实例 | 单进程 Playwright，每个会话一个 context | 换远程浏览器池（Playwright Server / Selenium Grid），`player_sim_agent` 的 `_run_session` 只依赖 `page` 接口，替换执行层即可 |
| LLM 决策成本 | 关键决策点按概率调 LLM，有预算护栏（`SIM_LLM_BUDGET`） | 改成"小模型本地推理"或"行为克隆模型"，把决策成本降到可忽略 |
| 事件写入 | 单表批量写入 | 改消息队列 + 时序库，或按 player_id 分片 |

**重要的是协议层不用动**：`player_sim_agent` 的输入仍是"部署 URL + 并发参数"，输出仍是"事件流"，扩到 1000 并发只换执行层。
