# 游戏研发自动化 Agent —— 需求理解与方案定位

> **阅读约定**：技术标识符首次出现时附中文注释，写法如 `A2A`（Agent-to-Agent，智能体间通信协议）、`artifact`（产物文件），后续不再重复注释。
> **口径约定**：本文所有"已实现"均指在本机（16 GB 内存 / 集显笔记本）真实跑通的链路，可在 `docs/03-实测验证与能力边界.md` 中逐条复现；未落地的一律标注"规划"。

---

## 一、结论先行

面试里那段对话，真正要解决的问题不是"做一个会写游戏的 Agent"，而是**把游戏研发中最贵的两段时间压缩掉**：

1. **从想法到可玩样本的时间**：策划口头描述 → 需求文档 → 开发排期 → 首个可跑版本，通常是"周"级。
2. **从可玩样本到"值不值得继续投入"的判断时间**：靠真人内测、买量小规模投放，通常是"周~月"级，且样本量有限。

本次 Demo 的定位是：**用一条 A2A 多智能体流水线，把这两个时间各自压到"分钟级/小时级"的可验证形态**，并且在设计上明确区分"AI 生成"与"真实市场结论"——前者可以流水线化，后者只能靠真实玩家数据，AI 只能提供**低成本的先验筛选**。

一句话概括方案：

> 自然语言需求 → 结构化规格契约（可执行验收断言）→ 编码与素材并行生产 → 真实浏览器盲测 + 静态审查 → 失败按产物所有权路由回生产者修复 → 合成玩家并发实验 → 指标报告 → H5/APK 交付，全流程由 A2A 协议编排、全链路留证据。

## 二、把面试原话拆成四层目标

面试官的原话里其实叠了四件不同的事，混在一起做会得到一个"什么都做一点、什么都不硬"的 Demo。下表把它们拆开，并给出本次的取舍。

| # | 面试原话（要点） | 真实业务诉求 | 本次 Demo 的落点 | 状态 |
|---|---|---|---|---|
| 1 | "输入一个游戏需求，Agent 自动完善需求，再编码、测试，交出最小 MVP" | **需求→可玩样本** 的全流程自动化，且要"能跑、能判定合格" | `orchestrator`（编排器）+ `spec_agent`（规格）+ `engineer_agent`（编码）+ `qa_agent`（运行时验证）+ `reviewer_agent`（静态审查） | 已实现并跑通 |
| 2 | "3D 建模一个角色、测试一个、coding 一个，还能补什么角色" | 角色划分与职责边界，避免一个巨无霸 Agent | 8 个执行角色 + 1 个编排角色（详见第四节） | 已实现 |
| 3 | "以后想用 AI 测试游戏，先 100 个玩家，再上 1000 个，验证喜不喜欢、愿不愿意付费" | **AI 玩家做规模化体验验证**，替代/前置真人外挂测试 | `player_sim_agent`（并发玩家模拟）+ `market_agent`（指标与报告），8~10 并发 × 多会话起步 | 部分实现：机制通用，规模与保真度是规划 |
| 4 | "多模态：生成图片、生成模型、调 3D、打包安卓 iOS、部署" | 多模态资产生产 + 构建发布链路 | `modeler_agent`（文生图/文生 3D 预留）+ `build_agent`（H5 部署 + Capacitor 打 APK） | 部分实现：文生图可开关、3D 为接口预留、iOS 仅接口 |
| 5 | "我们还有一些前端的工作" | 过程可见、结果可验收，不只是命令行输出 | Streamlit 控制台（任务时间线 / 断言明细 / 留存漏斗图 / APK 下载 / 游戏 iframe 预览） | 已实现 |

**取舍原则**：第 3、4 项是"未来要做大"的部分，Demo 阶段不追求规模，而是**把接口、数据结构、证据链先立住**，让后续扩到 100/1000 并发时只换执行层、不动协议层。

## 三、为什么是"多 Agent + A2A"，而不是一个大 Agent

这是面试官最可能追问的点，也是架构成立与否的关键。

| 维度 | 单 Agent（一个大 prompt 干到底） | 多 Agent + A2A（本方案） |
|---|---|---|
| 失败定位 | 只有"最终产物不对"，不知道错在规格、代码还是测试 | 每步有独立输入/输出与证据，能定位到具体断言、具体机制 |
| 质量门禁 | 模型自己说"我写好了" | 由**独立的验证角色**判定，生产者不能给自己发合格证 |
| 修复成本 | 全量重生成，容易越修越坏 | 只把失败断言路由回**产物所有者**，其余保持稳定 |
| 能力扩展 | 加能力 = 改 prompt，越改越脆 | 加角色 = 加一个 A2A 服务，注册 Agent Card 即可被发现 |
| 异构模型/工具 | 一个模型扛所有任务，成本高 | 编码用强模型、分类用小模型、素材走多模态 API，按需分配 |
| 可观测性 | 黑盒 | 每个角色独立日志、独立产物版本、独立耗时 |

代价也要说清楚：**多 Agent 的通信与状态一致性成本高**，所以本方案在三个地方做了硬约束——统一产物所有权表、统一状态机、统一契约（`app/contracts.py`），否则多 Agent 只会把混乱放大。

## 四、角色最小集：8 + 1

面试官问"角色定义要哪几个"（原话里的 ACM 指的就是这组 Agent 角色），我的答案是**按"产物所有权"划分，而不是按"技能"划分**——每个角色必须独占一类产物，否则修复时无法确定该回退给谁。

| # | 角色（Agent） | 端口 | 独占产物 | 一句话职责 | 为什么必须是独立角色 |
|---|---|---|---|---|---|
| 0 | `orchestrator` | 9000 | 任务状态、检查点 | 意图识别、路由、修复轮次、状态机 | 编排逻辑一变就影响全局，必须与执行解耦 |
| 1 | `spec_agent` | 9001 | 规格 JSON、验收断言、机制依赖 | 把口语需求变成可执行契约 | 契约是后续所有判定的唯一标准，不能被编码侧"顺手改" |
| 2 | `engineer_agent` | 9002 | `game.html` 及版本 | 按规格生成可玩游戏，按失败断言修复 | 唯一"能改代码"的角色，修复责任可追溯 |
| 3 | `modeler_agent` | 9003 | `assets/`（PNG/GLB/清单） | 多模态素材生产与降级 | 素材链路依赖外部 API，与代码生成解耦才能独立降级 |
| 4 | `qa_agent` | 9004 | 断言结果、截图、运行日志 | 真实浏览器里跑通、判定通过/失败 | **验证者不能是生产者**，否则质量门禁失效 |
| 5 | `reviewer_agent` | 9005 | 静态审查报告 | 契约完整性、离线性、外部依赖、风险点 | 静态问题（如引用不存在的资产）运行时未必暴露 |
| 6 | `player_sim_agent` | 9006 | 玩家行为事件流 | 并发模拟玩家，产出可分析的行为日志 | 规模与玩法无关，可独立扩容到 100/1000 |
| 7 | `market_agent` | 9007 | 验证报告 | 留存、付费漏斗、流失点、改进建议 | 指标口径必须与"生成"解耦，否则容易自证 |
| 8 | `build_agent` | 9008 | H5 包、部署 URL、APK | 打包、部署、安装包构建 | 构建环境重（SDK/Gradle），独立进程隔离风险 |

**为什么不再加角色**：`scene_agent`（关卡设计）、`balance_agent`（数值平衡）在 Demo 阶段会退化成"往 spec 里多写两段话"，收益低于通信成本；等规格契约扩展到关卡/数值维度后再拆，才是合理的拆分时机。

**关于面试官提的"3D 建模角色"**：本方案把它归入 `modeler_agent` 的 `_text_to_3d` 分支而不是单独角色——因为它与 2D 素材共享"输入规格 → 输出资产文件 + 元数据清单"的同一个契约，拆成两个角色只会让编排多一跳，不产生新的判定能力。

## 五、六个关键设计判断（面试可直接讲）

1. **契约先行，禁止"口头合格"**
   规格被固化成 `GameSpecContract`（游戏规格契约），断言类型限定在 `start / controls / score / win / win_text / lose` 六种可执行检查内，模型输出再花哨也只能落在这六类里。写不出可执行断言的规格直接判失败，而不是"先跑起来再说"。

2. **验证与生产分离，证据链可复现**
   QA 在真实 Chromium 里操作：状态机用 `window.__game`（页面暴露的游戏控制接口）驱动，移动用真实方向键事件，胜利文案必须同时满足"状态为 win + DOM 可见 + 文本与规格一致"。曾出现过"状态写了 win 但文案没显示"的假通过，这条正是为此加的硬门禁（`tests/test_qa_runtime.py` 里有对应反例测试）。

3. **修复回产物所有者，且必须带上一版代码**
   失败断言按所有权表路由回 `engineer_agent`，同时携带上一版产物与"受影响机制"，避免"重写一遍把已通过的断言弄坏"。修复轮次有上限 `MAX_FIX_ROUNDS`（默认 2），到顶仍不通过就**判失败**，不伪装成功。

4. **静态审查与运行时验证同为门禁**
   早期版本里静态审查只"记录不阻断"，导致资产缺失（引用了不存在的 PNG）也能交付。现在 `reviewer` 的 error 级问题会直接阻塞交付，并触发 `modeler_agent` 重建资产。

5. **存储分层 + 全链路降级**
   MySQL / Redis / Neo4j / Milvus Lite 任一不可用时自动降级（SQLite / 内存 / JSON 文件 / numpy 向量），保证 demo 在任何机器上能跑通；但降级会写进健康检查接口，**不隐藏**。

6. **明确区分"合成实验"与"真实市场结论"**
   玩家模拟与留存/付费指标来自**合成行为**，报告里显式标注"非真人实验"。它的作用是**先验筛选与假设生成**（哪一步流失最多、哪个机制最可能劝退），不能替代真实投放。

## 六、这次没有做、但要知道为什么（能力边界）

| 边界 | 现状 | 原因 | 何时该补 |
|---|---|---|---|
| 生成的是 Canvas 单页小游戏 | 支持"接金币"类核心循环 | 目标是验证流水线而非引擎能力 | 接 Phaser/Pixi 模板与资源管线后扩展品类 |
| 3D 资产 | 接口预留 + 占位 GLB | 本地无 GPU（集显 128 MB），文生 3D 需要外部服务 | 接 Tripo/Hunyuan3D 等 API，或改云侧生成 |
| APK | Capacitor + Gradle 真实构建，依赖本机 Android SDK | 16 GB 内存 + 集显，构建重 | 迁到 CI（GitHub Actions/云构建机） |
| AI 玩家规模 | 实测 8~10 并发（`SIM_CONCURRENCY` 默认 10，会话数 `SIM_SESSIONS_PER_PLAYER`）；16 为配置上限、未压测 | 单进程 Playwright 的 CPU/内存上限 | 改成远程浏览器池或轻量客户端 SDK 后上 100/1000 |
| iOS | 仅接口预留 | 需 macOS + Xcode | 接云打包（如 Bitrise/Codemagic） |
| 真实运营数据 | 无 | Demo 无线上投放 | 接埋点/归因后，用真实数据校准指标口径 |

> 这份边界表是主动写的，不是被问出来的。面试里主动交代边界，比被追问"这个能上生产吗"要安全得多。

## 七、和公司需求的对应关系

| 公司的诉求 | 本 Demo 的对应实现 | 可继续深化的方向 |
|---|---|---|
| 需求自动完善 | `spec_agent`：口语 → 结构化规格 + 可执行断言 + 机制依赖图，RAG 参考引擎文档与设计模式 | 引入策划知识库、竞品拆解、数值模板 |
| 自动编码 | `engineer_agent`：LLM 生成 + 契约校验，失败降级到确定性模板 | 多品类模板库、代码静态分析前置 |
| 自动测试 | `qa_agent` 真实浏览器断言驱动 + `reviewer_agent` 静态审查 | 探索式测试（随机走查 + 覆盖率引导） |
| AI 玩家验证 | `player_sim_agent` 并发模拟 + `market_agent` 留存/付费/流失 | 从"规则+LLM 决策"升级为"行为克隆 + 强化学习"玩家 |
| 多模态 | `modeler_agent`：文生图（万相）+ 文生 3D 接口 + 程序化降级 | 接 3D 生成服务、音频与动效生成 |
| 构建发布 | `build_agent`：H5 部署 + APK 构建 + iOS 接口 | CI/CD 流水线、灰度发布 |
| 前端 | Streamlit 控制台：时间线、断言明细、图表、预览 | 换 React 前端 + WebSocket 实时推送 |
